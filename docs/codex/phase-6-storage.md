# 第六批：历史存储、查重和搜索

## 图片存储与迁移

- `History.sqlite3` 保留原有的 `clips` 和 `metadata`。卡片继续使用二进制 Property List。图片载荷保留原来的类型和格式，字节字段置空。文件卡片的快照字段留空。两个可选图片引用各自保存原字节数、格式、SHA-256 摘要，以及在 ImageIO 能解析时得到的宽高。
- `clip_blobs` 以卡片 ID 和用途（原图或快照）为主键，保存摘要和原始字节。写入卡片与图片共用事务。替换图片会移除旧版本，删除卡片会级联删除图片。读取按卡片 ID、用途、摘要和字节数核对引用。普通历史 64 MiB、收藏 32 MiB、单条 8 MiB 继续按原始内容字节计量。
- 首次可写打开旧 SQLite 库时，按行迁移内嵌图片，保留卡片 ID、位置、时间和其他元数据。整批迁移和完成标记共用事务。失败时回滚并读取原有内嵌图片，下次打开再尝试。只读客户端可直接读取旧行。数据库写入新格式时使用 `user_version = 2`。旧 `History.plist` 继续走原导入入口，导入时同步写入图片表。
- 新捕获的图片在异步写入完成前由卡片和写入队列共享。提交后释放暂存字节。粘贴、拖出、预览、OCR、二维码识别和同步导出按需解析引用。缩略图渲染先查现有的 `NSCache`，MCP 优先使用已存图片尺寸和字节数。粘贴栈和删除撤销在用户操作时取一份副本，可以跨历史清理使用。RTF、HTML 继续随文字卡片保存，Markdown 和 HTML 源码导出沿用这些字段。

## 查重

`contentHash` 为可选字段。SHA-256 覆盖载荷类型、原始内容、格式和快照，字符串使用 Unicode 规范组合形式。值按长度分隔，缺失值有独立标记。旧卡片在同类内容首次查重时补算，图片摘要可直接从引用取得。相同摘要才读取内容并执行原有相等比较。

## 搜索

运行时检查 `ENABLE_FTS5`，并探测 SQLite 是否支持 trigram。索引包含标题、OCR 文本、二维码内容、载荷可搜索文本和来源。旧库首次打开时补建。单独的整数行号表允许卡片移动位置时保留 FTS 行号。索引和卡片在同一事务更新，提交标记用于核对内存快照对应的索引版本。索引更新失败会清除标记，后续可写打开会重建。FTS5 的三字符分词机制见 [SQLite FTS5 文档](https://sqlite.org/fts5.html#the_trigram_tokenizer)。

历史超过 2,000 条、查询有至少三个可索引字符且索引版本对应时，先取候选 ID。对 ASCII 和基本汉字做保守的归一化，丢弃 ASCII 空白和标点以放宽候选范围。包含重音、全角字符、组合标记等其他字符的记录总会纳入候选。短查询、无法归一化的查询、不可用或尚未提交的索引继续走内存扫描。所有候选仍由 Foundation 的 `localizedStandardContains` 和原有筛选条件复核，沿用历史或钉板顺序。匹配行为见 [Apple Foundation 文档](https://developer.apple.com/documentation/foundation/nsstring/localizedstandardcontains(_:))。
